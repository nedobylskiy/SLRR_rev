# Maps: first pass on Test Track

The original `sl/Scripts/game/src/TestTrack.java` selects `maps.test_track:0x00000001r`, which is the root of `maps/test_track.rpk`. The installed package contains 344 entries: one type 1 root, 170 type 5 mesh entries, 169 type 14 render entries, and several auxiliary resources. The render root has `Test_track` ID `0x14`; it itself and its 167 child render records reference external models via the `mesh` property. The separate entry `minimap` is not included in the scene geometry.

The new loader goes through these links in the RPK and opens the original SCX and textures from the game installation. The vertices of the sections already contain map coordinates in centimeters, so the general scale `0.01` is applied to the model node, without manual placement of objects and corrections for a specific car. The local Test Track loads 168 models and 67,021 triangles. The scene is accessible by the “Test Track” button.

The previously missed ring road is `palya.scx` (11,295 triangles). In the RDB, the resource `0x15` points to `palya.scx`, and the collected RPK points to the eponymous `palya.scY`: this SCY contains materials without triangles. If there is an SCX next to the SCY, the loader takes the geometry from it. The `0x14` render record has one zero terminator after the text RSD, which previously erroneously marked the entire record as binary. Both fixes are based on resource properties, without a list of map model names.

For the test ride, SCX triangles are indexed into 16 m cells. Vertical sampling gives the height and normal of the ascending surface; the beams of four wheels and body contact work on it. There are 48,467 such triangles indexed on the local map. When the soil and separate ground mesh overlap, the top surface below the query point is selected: this allows the wheel to use the wooden `Box10/Box11.scx` flooring instead of the asphalt underneath. Another 20,538 side triangles are indexed in 8 m cells for two-way contact of the body with fences and buildings. Start `0, -1461.785` and direction `3.14` are taken from the 1/4 mile straight at `TestTrack.java`. The exit point `(-456, 0, -584)` is now also covered by a road, but the start on a straight line is retained in the demo.

An RSD block was found in the binary contents of the root `test_track.rpk`, but the PHYS/POLY signatures were missing from all of its entries. The physics model is now derived **from the original SCX mesh** rather than from a separate original physics layer. It maintains the height of the road and contacts of the body with the side edges; There is no continuous detection of high-speed collisions, contact of wheels with vertical walls, multi-level vertical sampling, objects from binary blocks and game logic of the race. There is no invisible plane outside the extracted surface. The differences between visual and in-game collision, including the wooden ramp, are explored separately in [map physics breakdown](map-physics-investigation.md).

Child render resources are selected by type and `superId`, not by `area_*` names or a hard-coded Test Track file list. The same traversal works for other maps using this RPK scheme when their SCX files are supported by the parser.

## Markings, emblems and lighting by time of day

Some road images are stored **in SCX materials** rather than as separate objects from `decals.rpk` (this package also applies to car decals). For example, `area_1934.scx` refers to the grass `area.dds` and the second layer to `invictus_racing500.dds`, `ReallyFast_Text.dds` and `DragRacingofStates.dds`. `area_2035.scx` also features the Invictus emblem. Other fragments use `parkolo01.dds` and `TestTrackRoad.dds` for road markings. In v3 materials, the index of the second layer is at offset +52, and the UV channels of both maps are explicitly specified in the extended material (+70/+72). `area_1810.scx` is especially important to read with the flags: `cross.dds` contains RGB asphalt with almost zero alpha; the main alpha flag is not set, and `0x40` mixes `parkolo01.dds` on top of it. Ignoring the flag created dark holes in the parking lot. The loader now restores both textures without separate coordinates or corrections for this map. The scene also has independent models `Invictus_RAcing500/501/502.scx`; they should not be confused with a large image on the surface.

For time of day, the primary available source is `sl/Scripts/game/src/Scene.java`: `time2Config()` selects one of 15 options, and `addSceneElements()` for each sets fog, directional/background light color, sky resource and global environment map from `maps/skydome.rpk`. `TestTrack.java` calls this common logic through `Track.enter()`. These are **lighting and sky sets**, not the confirmed 15 shadowmap files. Automatic audit of `npm run audit:map-lighting` passed RPK→SCX→texture connections for **168 models and 550 materials** Test Track: among the recognized main and second texture layers there are no links to files with `lightmap`/`shadow` in the name. **11 types of placed objects** (13 materials) were also checked: there are no such links among their recognized texture layers either. All five fields `shd_center`, `shd_diru`, `shd_dirv`, `shd_vbase`, `shd_vup` are present in **169** RDB render records and **zero everywhere**. There is an additional UV channel in many SCXs, but for example `palya.scx` selects channel 2 for the regular `cross.dds`; the presence of a UV by itself does not prove a separate lightmap. The general `maps/textures.rpk` has files with `lightmap` and `shadow` in their names, but Test Track's ground render models do not reference them. Checking the maps `city`, `city2` and `ROC_track` by the same team also did not reveal such links among their ground render models. This does not exclude native dynamic shadows or resources that our loading scheme does not yet detect; they need to be examined separately. Our WebGL renderer still uses constant light. The assumption that Test Track was the developer's first map is not supported by these data.

Additional parsing of `npm run audit:lightmap-usage` revealed **14 DDS** with `lightmap` in the name in the shared library `maps/textures.rpk`; [machine report](reports/lightmap-usage.json) shows 25 render resources `objects.rpk`, referencing 8 of them. There are 26 actual applications found in the materials of these SCXs: 10 with card type `0x06000004` and 16 with `0x06000005`. Example - `krthaz02.scx`: The window material uses `ablakok02.dds` as the base layer and `lightmap_ablakok02.dds` as `0x06000004`; the `krthaz02_night.scx` option uses the same DDS via `0x06000005`. In appearance, the file represents a mask of illuminated windows on a black background. The type numbers and the day/night pair indicate different rules for mixing the light layer, but the exact formulas of the original render have not yet been restored. The parser now preserves both properties; The WebGL pass does not impose them yet.

When resolving actually placed objects, `city` uses **seven** of such materials (`0x06000005`, windows and facades), and `city2` uses **five** (`0x06000004`, house windows). Test Track uses **zero** in both ground models and placed objects. In each of the two cities, three more objects were missed due to the unsupported `render` field in the CFG, so the numbers refer to successfully resolved objects. Thus, support for local light maps for urban objects has been confirmed, but there is still no confirmation of a separate set of global shadowmaps for each hour of the day. The remaining six named DDS are registered in the library, but no references to them were found from the RPK/RDB searched.

Individual route objects—trees, lights, signs, and containers—are described in the original `maps/test_track.rdb` as instances of `typeof 1` with `gametype` and six coordinates `params`. The compiled RPK does not have these instances, so the loader now reads the available RDB, resolves `gametype` through the RPK's dependency table, reads the compiled `ICFG` of the object, and uses its `render`/`body`. On the local Test Track, 1413 instances of 11 types are resolved this way, including 80 containers. Repeating patterns are drawn using `InstancedMesh`; `body ... box` forms provide oriented static contacts of the body and wheel support on the upper surface. The beam checks the rotated CFG box in its coordinate system; the underside does not become road surface. This is a restoration based on the text source of the map; the coincidence of the RDB version with the RPK still needs to be checked on the original EXE. CFG forms other than `box` are not migrated.

To debug physics, the map has a collapsible “Map Wireframes” panel. It separately shows the green support triangles, orange side faces, and blue oriented CFG boxes. The lines are built from the same data that physics uses and are only created when the layer is turned on.

Tire marks and gray smoke on the ride take contact position, load and longitudinal/lateral slip from the physics of each wheel. The trace is laid according to the height and normal of the support grid. In the original `particles.rdb` for `skidmark` `particles/textures/skidmarks/sliding/asphalt.png` and `grass.png` are registered; `asphalt.cfg` defines different areas of this atlas as `uv_end` and `uv_normal`. Reading the entire picture in a row produced a noticeable dotted line due to the transparent gaps, so a continuous stripe is drawn on the road and grass with gradual transparency at the beginning and end. For the clearly named loose soil, the original texture `grass.png` is loaded. Since part of the map uses mixed atlases (eg `area.dds`), the unknown material is considered to be a road version. The mark appears only with pronounced sliding, and smoke occurs with even stronger longitudinal slipping, in portions; the particles expand as they move away from the wheel. This is only a visual effect: the texture classification does not change the adhesion strength and does not claim to be a restored system of coating types of the original EXE. The number of segments and particles is limited; Resetting the trip clears them.

Visual instances load gradually near the vehicle: model bytes are requested when an instance enters the streaming radius, then at most 48 instances are activated per frame. The default radius is 500 m and the debug panel adjusts it live from 200 to 2000 m. Residency has a 100 m hysteresis margin and unused model resources are released after five seconds. Static map chunks also load their visual geometry/textures on demand; the physical map index remains resident.

Rendering is independent of residency. Each loaded instance is tested against the current camera frustum using its transformed model bounds, rather than submitting all instances of a model whenever their combined sphere intersects the screen. Only visible, in-range instances are uploaded into the draw batch. Camera turns reuse resident models; unchanged visible sets do not reupload matrices. Shrinking the radius immediately changes draw eligibility, without waiting for memory eviction. Debug counters show submitted instances, resident instances and total indexed placements. A large SCX chunk still streams as a whole: touching its bounds can load geometry farther away than the radius. This is conservative culling, not occlusion culling or LOD.

Fog is controlled independently through `MapFogSettings` and the original Java scene calls (fallback profile: 260–900 m). Reducing render/stream range may have little effect on FPS when physics or another CPU task dominates the frame, even if submitted geometry and memory usage decrease.

Map CFG `rendertypes` tables override the preceding `render` placeholder. For example, `18x6_haromboltiv.cfg` places a component at height 6.5 m with placeholder `0x1de` (an entrance mesh), but its variant table references canopy meshes `homlok12a` through `homlok12f` and empty entries. Ignoring this table produced floating entrances. The map loader now uses variant zero, retains the original component pose, and skips zero resource entries. Original per-instance variant selection and synchronization with day/night variants are still pending; all instances currently share the first configured variant.

The map debug panel also provides independent lighting comparisons:

- **Dynamic lighting** (on by default) applies the renderer's sun, ambient illumination and material reflections. Turning it off shows diffuse textures/colors with emissive contributions and fog retained. Java scene light updates continue to be stored.
- **Shadow maps** (off by default) enables a new 2048×2048 directional sun shadow map covering a 200 m square around the vehicle. This is renderer-generated shading, not restored original baked shadow textures. Nearby off-screen instances within 150 m stay submitted as potential shadow casters; enabling this option adds rendering cost.
- **Vertex colors (experimental)** (off by default) applies SCX vertex RGB independently of dynamic lighting. V3's packed word at vertex offset 40 and V4's diffuse color field (flag `0x80`) are interpreted as ARGB; vertex alpha and V4 specular colors are not applied. For V3 materials with flag `0x100` and no alpha-opacity flag, texture alpha is interpreted as paint coverage: `mix(vertexRGB, textureRGB, textureAlpha)`. This preserves opaque window pixels while coloring facade regions (for example `homlok5.dds` has alpha 0 on the wall and 255 on windows). Other materials multiply diffuse RGB by vertex RGB. This paint interpretation matches the observed texture masks and original-game reference; exact original blend-state semantics remain unconfirmed. Sky domes are excluded.
