# Карты: первый проход на Test Track

Исходный `sl/Scripts/game/src/TestTrack.java` выбирает `maps.test_track:0x00000001r`, то есть корень `maps/test_track.rpk`. В установленном пакете 344 записи: один корень типа 1, 170 mesh-записей типа 5, 169 render-записей типа 14 и несколько вспомогательных ресурсов. У render-корня `Test_track` ID `0x14`; он сам и 167 его дочерних render-записей ссылаются через свойство `mesh` на внешние модели. Отдельная запись `minimap` не входит в геометрию сцены.

Новый загрузчик проходит эти связи в RPK и открывает исходные SCX и текстуры из установки игры. Вершины участков уже содержат координаты карты в сантиметрах, поэтому на узел модели применяется общий масштаб `0.01`, без ручной расстановки объектов и поправок под конкретную машину. На локальном Test Track загружается 168 моделей и 67 021 треугольник. Сцена доступна кнопкой «Тестовый трек».

Пропущенная ранее окружная дорога — `palya.scx` (11 295 треугольников). В RDB ресурс `0x15` указывает на `palya.scx`, а собранный RPK указывает на одноимённый `palya.scY`: этот SCY содержит материалы без треугольников. Если рядом с SCY существует SCX, загрузчик берёт геометрию из него. Render-запись `0x14` имеет один нулевой терминатор после текстового RSD, который раньше ошибочно помечал всю запись бинарной. Оба исправления основаны на свойствах ресурсов, без списка имён моделей карты.

Для тестовой поездки SCX-треугольники индексируются по ячейкам 16 м. Вертикальная выборка даёт высоту и нормаль восходящей поверхности; на ней работают лучи четырёх колёс и контакт кузова. На локальной карте индексировано 48 467 таких треугольников. Когда грунт и отдельный ground-меш перекрываются, выбирается верхняя поверхность ниже точки запроса: это позволяет колесу использовать настил деревянных `Box10/Box11.scx` вместо асфальта под ним. Ещё 20 538 боковых треугольников индексированы по ячейкам 8 м для двухстороннего контакта кузова с ограждениями и постройками. Старт `0, -1461.785` и направление `3.14` взяты из прямой 1/4 мили в `TestTrack.java`. Точка выхода `(-456, 0, -584)` теперь тоже покрыта дорогой, но в демонстрации сохранён старт на прямой.

В бинарном содержимом корня `test_track.rpk` обнаружен блок RSD, но сигнатуры PHYS/POLY отсутствуют во всех его записях. Физическая модель сейчас получена **из исходной сетки SCX**, а не из отдельного оригинального физического слоя. Она поддерживает высоту дороги и контакты кузова с боковыми гранями; пока нет непрерывного обнаружения высокоскоростных столкновений, контакта колёс с вертикальными стенами, многоуровневой вертикальной выборки, объектов из бинарных блоков и игровой логики заезда. За пределами извлечённой поверхности нет невидимой плоскости. Различия между визуальной и игровой коллизией, включая деревянную рампу, исследуются отдельно в [разборе физики карт](map-physics-investigation.md).

Выбор дочерних render-ресурсов сделан через типы и `superId`, а не по именам `area_*` или списку файлов Test Track. Такой же проход подходит другим картам с этой схемой RPK, если их SCX поддерживаются текущим парсером.

## Разметка, эмблемы и освещение по времени суток

Некоторые дорожные изображения хранятся **в материалах SCX**, а не как отдельные объекты из `decals.rpk` (этот пакет относится также к наклейкам на машины). Например, `area_1934.scx` ссылается на траву `area.dds` и вторым слоем на `invictus_racing500.dds`, `ReallyFast_Text.dds` и `DragRacingofStates.dds`. В `area_2035.scx` также встречается эмблема Invictus. Другие фрагменты используют `parkolo01.dds` и `TestTrackRoad.dds` для дорожной разметки. В материалах v3 индекс второго слоя стоит по смещению +52, а каналы UV обеих карт явно указаны в расширенном материале (+70/+72). `area_1810.scx` особенно важно читать с флагами: `cross.dds` содержит RGB-асфальт под почти нулевой альфой; флаг основной альфы не установлен, а `0x40` смешивает поверх него `parkolo01.dds`. Игнорирование флага создавало тёмные дыры на стоянке. Загрузчик теперь восстанавливает обе текстуры без отдельных координат или поправок для этой карты. У сцены также есть самостоятельные модели `Invictus_RAcing500/501/502.scx`; их нельзя путать с большим изображением на поверхности.

Для времени суток первичный доступный источник — `sl/Scripts/game/src/Scene.java`: `time2Config()` выбирает один из 15 вариантов, а `addSceneElements()` для каждого задаёт туман, цвет направленного/фонового света, ресурс неба и глобальную environment map из `maps/skydome.rpk`. `TestTrack.java` вызывает эту общую логику через `Track.enter()`. Это **наборы освещения и неба**, а не подтверждённые 15 файлов shadowmap. Автоматический аудит `npm run audit:map-lighting` прошёл связи RPK→SCX→текстуры для **168 моделей и 550 материалов** Test Track: среди распознанных основного и второго текстурных слоёв нет ссылок на файлы с `lightmap`/`shadow` в имени. Проверены и **11 типов размещённых объектов** (13 материалов): среди их распознанных текстурных слоёв таких ссылок также нет. Все пять полей `shd_center`, `shd_diru`, `shd_dirv`, `shd_vbase`, `shd_vup` присутствуют в **169** render-записях RDB и **везде нулевые**. Дополнительный UV-канал есть во многих SCX, но, например, `palya.scx` выбирает канал 2 для обычной `cross.dds`; наличие UV само по себе не доказывает отдельную карту освещения. В общей `maps/textures.rpk` есть файлы с `lightmap` и `shadow` в именах, но наземные render-модели Test Track на них не ссылаются. Проверка карт `city`, `city2` и `ROC_track` той же командой тоже не выявила таких ссылок среди их наземных render-моделей. Это не исключает нативных динамических теней или ресурсов, которые наша схема загрузки пока не обнаруживает; их нужно исследовать отдельно. Наш WebGL-рендер по-прежнему использует постоянный свет. Предположение, что Test Track была первой картой разработчика, эти данные не подтверждают.

Дополнительный разбор `npm run audit:lightmap-usage` выявил **14 DDS** с `lightmap` в имени в общей библиотеке `maps/textures.rpk`; [машинный отчёт](reports/lightmap-usage.json) показывает 25 render-ресурсов `objects.rpk`, ссылающихся на 8 из них. В материалах этих SCX найдены 26 фактических применений: 10 с типом карты `0x06000004` и 16 с `0x06000005`. Пример — `krthaz02.scx`: материал окна использует `ablakok02.dds` как основной слой и `lightmap_ablakok02.dds` как `0x06000004`; вариант `krthaz02_night.scx` использует тот же DDS через `0x06000005`. По виду файл представляет маску освещённых окон на чёрном фоне. Номера типов и пара day/night указывают на разные правила смешения светового слоя, но точные формулы исходного рендера ещё не восстановлены. Парсер теперь сохраняет оба свойства; WebGL-проход пока их не накладывает.

При разрешении реально размещённых объектов `city` использует **семь** таких материалов (`0x06000005`, окна и фасады), а `city2` — **пять** (`0x06000004`, окна домов). Test Track использует **ноль** и в наземных моделях, и среди размещённых объектов. В каждом из двух городов ещё по три объекта пропущены из-за неподдержанного поля `render` в CFG, поэтому числа относятся к успешно разрешённым объектам. Таким образом, поддержка локальных световых карт у городских объектов подтверждена, но подтверждений отдельного набора глобальных shadowmap под каждый час суток всё ещё нет. Остальные шесть названных DDS зарегистрированы в библиотеке, но ссылок на них из просмотренных RPK/RDB не найдено.

Отдельные объекты трассы — деревья, фонари, знаки и контейнеры — описаны в исходном `maps/test_track.rdb` как экземпляры `typeof 1` с `gametype` и шестью координатами `params`. В собранном RPK эти экземпляры отсутствуют, поэтому загрузчик теперь читает доступный RDB, разрешает `gametype` через таблицу зависимостей RPK, читает скомпилированный `ICFG` объекта и использует его `render`/`body`. На локальном Test Track так разрешаются 1413 экземпляров 11 типов, в том числе 80 контейнеров. Повторяющиеся модели рисуются через `InstancedMesh`; формы `body ... box` дают ориентированные статические контакты кузова и опору колёс на верхней поверхности. Луч проверяет повёрнутую CFG-коробку в её системе координат; нижняя сторона не становится дорожным покрытием. Это восстановление по текстовому источнику карты, совпадение версии RDB с RPK ещё нужно проверить на оригинальном EXE. Прочие формы CFG, кроме `box`, не перенесены.

Для отладки физики у карты есть сворачиваемая панель «Каркасы карты». Она отдельно показывает зелёные опорные треугольники, оранжевые боковые грани и голубые ориентированные CFG-коробки. Линии строятся из тех же данных, которые использует физика, и создаются только при включении слоя.

Следы шин и серый дым в поездке берут положение контакта, нагрузку и продольное/боковое скольжение из физики каждого колеса. След укладывается по высоте и нормали опорной сетки. В оригинальном `particles.rdb` для `skidmark` зарегистрированы `particles/textures/skidmarks/sliding/asphalt.png` и `grass.png`; `asphalt.cfg` задаёт разные области этого атласа как `uv_end` и `uv_normal`. Чтение всей картинки подряд давало заметный пунктир из-за прозрачных промежутков, поэтому на дороге и траве рисуется непрерывная полоса с постепенной прозрачностью на начале и конце. Для явно названного рыхлого грунта загружается оригинальная текстура `grass.png`. Поскольку часть карты использует смешанные атласы (например, `area.dds`), неизвестный материал относится к дорожному варианту. След возникает лишь при выраженном скольжении, а дым — при ещё более сильной продольной пробуксовке, порциями; частицы расширяются по мере удаления от колеса. Это только визуальный эффект: классификация текстуры не меняет силы сцепления и не претендует на восстановленную систему типов покрытий оригинального EXE. Число сегментов и частиц ограничено; сброс поездки очищает их.

Визуальные экземпляры объектов теперь появляются постепенно вокруг камеры: модель типа загружается при приближении к его экземпляру, затем за кадр активируется не более 48 экземпляров. За пределами радиуса они убираются из отрисовки, а статическая коллизия остаётся в индексе карты. HUD поездки показывает число активных объектов. Туман начинает скрывать дальние объекты с 260 м и полностью закрывает их к 900 м; стриминг работает чуть дальше границы тумана, чтобы объект успел появиться до того, как станет видимым. Цвет и расстояния находятся в отдельном профиле `MapFogSettings`, который позже можно будет заполнять из игровых скриптов. Дальние объекты пока используют тот же меш: отдельного LOD нет. Основные SCX-участки земли и их физический индекс сейчас загружаются целиком.
