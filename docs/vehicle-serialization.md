# Состояние автомобиля: память, SDAT и сеть

Главный приоритет проекта после уточнения владельца: избавиться от обязательного сохранения живого автомобиля на диск для передачи его состояния. По сообщению владельца, критический сбой старой реализации связан с утечкой при сохранении автомобиля. Эта причина не воспроизведена и не локализована в текущем исследовании; найденные ошибки libffi не выдаются за её объяснение.

Новый контракт: **capture в конце simulation tick → автономный byte buffer → транспорт → validate/decode → подготовка ресурсов → атомарное восстановление**. Диск является необязательным потребителем того же буфера.

## Что установлено по старым Java

`sl/Scripts/game/src/Vehicle.java`: SAVEFILEID_VHC=0x88664422, SAVEFILEVERSION_VHC=5. `Vehicle.save(String)` открывает `java.io.File`, пишет идентификатор, версию, имя chassis, вызывает `chassis.save(File)`, затем пишет статистику. `Vehicle.load` читает в том же порядке, создаёт chassis через `Part.createFromFile`, затем `Vehicle`, восстанавливает статистику и вызывает `wakeUp`.

После chassis идут восемь float для рекордов трассы, races_won и races_lost (int), bestNightQM и valid (float). Это подтверждено исходником; расположение начала этой статистики нельзя искать как фиксированное смещение, потому что дерево деталей переменной длины.

`parts/scripts/src/Part.java`:

1. Resource ID типа детали и версия PART.
2. Texture RID, mesh RID, wear f32, tear f32.
3. Начиная с PART version 3 — две строки adjusted position и adjusted orientation.
4. Повтор слотов: slotIndex int; damage String; otherSlotID int. При otherSlotID!=0 рекурсивно записывается установленная деталь.
5. `-1` завершает слоты.
6. Подкласс добавляет собственные поля после `super.save`.

В загрузчике `Part.createFromFile` читается тип и версия, создаётся script instance, затем вызывается его виртуальный `load`. Без знания класса нельзя определить длину дополнительного хвоста и безопасно перескочить к следующему узлу. Плоский generic parser только базового Part будет ошибаться на двигателях, трансмиссии, шинах и модах.

`parts/scripts/bodypart/Src/Chassis.java` добавляет собственную версию 3: число колёс, строки повреждения каждого колеса (в обратном порядке индексов), brake_balance, mileage. Во время загрузки ставит `suspend_update`, после чтения вызывает `forceUpdate`. Это важный ориентир для транзакционного восстановления.

[Рабочий архив Elias](elias-workspace-archive.md) содержит разбор native `Chassis.getWheelDamage`/`setWheelDamage` для **другого EXE**. По его данным активность повреждения хранится отдельным битом в физической записи колеса, а строка переносит десять чисел, включая позу. Это ценная гипотеза для совместимого restore и сети; наш ограниченный source runtime пока правильно сохраняет строку непрозрачной и не интерпретирует её без проверки на целевой версии.

Линейная и угловая скорости не видны в этом верхнеуровневом Java-save. Старый гаражный файл нельзя автоматически считать полным динамическим состоянием автомобиля для гонки.

## SDAT — контейнер java.io.File

`src/formats/sdat.ts` читает envelope, не создавая native-объекты и не вызывая старый файловый код. Проверены **139 SDAT**, **64 заголовка Vehicle v5** и **1562 записи unsaved resources**. Их decode→encode полностью в памяти возвращает исходные байты побайтно (`npm run verify:saves`). Это проверка контейнера, а не декодирование всех полей деталей.

Заголовок 8 байт: `SDAT`, версия u16 0x0100, type u8 (1/2), flags u8. Полезные данные Java начинаются с +8. В конце лежит trailer, который native File открывает раньше, чем отдаёт скрипту readInt/readResID.

### Type 2

Последний u32 — размер trailer без самого этого слова. Начало: fileLength-4-trailerLength.

1. u32 число unsaved ресурсов.
2. Для каждого: ordinal u32, kind u32, payload size u32; у kind=7 идут bytes[size] изображения/текстуры. Другие непустые kind не поддерживаются и отклоняются.
3. u32 число пакетов.
4. Для каждого: ordinal u32, string length u32, path[length] с NUL.
5. u32 trailer length.

Type 1: перед последними двумя u32 хранится список пакетов; последние слова — remount bytes и pack count.

Числа File — little-endian i32/f32. String — u32 длина **с NUL**, затем bytes; length=0 значит null, length=1 с NUL — пустую строку. В отличие от CONS, здесь NUL входит в длину.

Сохранённый RID содержит file-local ordinal пакета в high16. Trailer восстанавливает путь; low16 остаётся локальным ID. hi=0/0xffff относится к transient/unsaved resources. Отправлять только runtime RID по сети нельзя: на другом клиенте тот же integer может обозначать другой пакет или ничего.

`serializeSdat(parseSdat(bytes))` сохраняет opaque payload и embedded textures, не декодируя детали. Это позволяет передавать **уже полученный** файл как буфер, но не устраняет утечку старого EXE при его первоначальном создании. Никакого утверждения об исправлении старого EXE здесь нет.

## Новый формат SRVS v1 — реализован

Код: `src/runtime/vehicle-state.ts`. Чистые функции `serializeVehicle(state)` и `deserializeVehicle(bytes, expectedContentHash?)`. Не используют fs, File.open или temporary files, не удерживают ссылку на исходный автомобиль.

В snapshot включены vehicle ID, tick, content manifest hash, root part ID; transform, linearVelocity, angularVelocity, rpm, gear; список деталей со стабильными ID, parent ID, парой слотов, ресурсом, mesh/texture override, transform, wear/tear, версией и JSON-состоянием скрипта.

| Смещение | Тип | Содержимое |
|---:|---|---|
| 0 | char[4] | SRVS |
| 4 | u32 LE | Версия 1 |
| 8 | u32 LE | Длина UTF-8 JSON payload |
| 12 | u32 LE | CRC32 payload |
| 16 | bytes[length] | UTF-8 JSON |

JSON выбран как прозрачный стартовый формат. Это не окончательная оптимизация bandwidth. CRC32 выявляет повреждение, **не** является аутентификацией. Транспорт обязан обеспечивать авторизацию и целостность. Максимальный payload 4 MiB, до 10000 деталей, ограниченная глубина script data; проверяются числа, кватернионы, уникальность ID, единственный корень, отсутствие циклов и потерянных родителей. Несовпадение contentHash отклоняется.

64-bit значения модов следует представлять строками с явным типом в собственной схеме: стандартный JSON number не гарантирует точности за пределами 2^53-1. Native pointers, runtime object handles, функции, файлы и GPU-объекты не сериализуются.

`MemoryFile` реализует совместимые примитивы int/float/String в собственном буфере. Это строительный блок для будущей реализации java.io.File поверх памяти. Набор native File ещё не привязан к TUFA VM. Кодировка старых строк пока Windows-1252; неподдержанные символы при записи отклоняются, а не заменяются молча.

## Что требуется для живого автомобиля

Обновление: ограниченный source runtime уже исполняет оригинальные Part/Chassis/Tyre/ShockAbsorber save/load на синтетической модели со слотами через память; восстановление транзакционное. [Описание и проверки](part-runtime.md). Это отдельная host-модель: адаптер к новому CFG-миру и SRVS ещё отсутствует. Ниже остаются требования к интеграции общего движка.

Capture adapter ещё отсутствует. Он должен прочитать всю модель автомобиля нового движка на границе tick, включить script-defined fields и созданные окраски, составить snapshot без ссылок на изменяемые объекты. Старый EXE, его heap и private native-структуры этот codec не читает.

Restore adapter тоже ещё отсутствует. Нужна подготовка без побочных эффектов: проверить схему/manifest, разрешить все ресурсы, выделить узлы, восстановить ссылки/слоты, применить настройки без forceUpdate на каждом поле, пересчитать физику один раз, затем заменить автомобиль в мире. При ошибке уничтожить только подготовленные ресурсы и оставить старый автомобиль рабочим.

Обязательно отдельно хранить attachments/damage/тюнинг/окраску и динамические величины. Полный baseline передаётся при появлении машины, смене конфигурации или reconnect. Частые сообщения движения должны быть меньше и ссылаться на версию baseline.

## Проверки памяти

Тест делает 1000 decode→encode, проверяя отсутствие накапливаемого состояния сериализатора и стабильность байтов. Это **не** доказательство отсутствия любых утечек в будущем runtime. Для живого мира нужны heap snapshots, counts объектов/тел/текстур, тесты rollback/удаления и повторные connect/disconnect, а для старого EXE — профилировщик аллокаций и воспроизводимый сценарий save.
