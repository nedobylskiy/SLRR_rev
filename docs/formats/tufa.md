# Java-диалект, TUFA и TREE

`.class` в этой игре не является стандартным Java classfile. Все 2921 локальных файла имеют `TUFA`, а не `CAFEBABE`. В них 2993 класса: один файл может содержать несколько последовательных TUFA-блоков. Реализация: `src/formats/tufa.ts`.

## Контейнер

Каждая секция: tag char[4], payload size u32 LE, payload[size]. Первая секция — `TUFA`, размер 4, затем u32 версия. Встречены 0x11ae1 (5 файлов), 0x24f5c (159), 0x24f9d (2757). Это версии формата/компилятора, а не доказательство версии игры.

Далее CONS, FILD, MTHD, CLSS, TREE в встречающемся порядке. Следующий `TUFA` начинает следующий класс. Парсер проверяет длину секций, не ищет магические строки внутри payload.

## CONS — пул констант

В начале u32 count. Каждая запись начинается **явным u32 kind**:

| kind | Payload |
|---:|---|
| 0 | u32 длина текста без NUL, bytes[length], NUL |
| 1 | u32 scalar bits; точная семантика требует анализа использования |
| 2 | u32 scalar bits; точная семантика требует анализа использования |
| 3 | u32 package-string index, u32 local resource ID |
| 4 | u32 string index для имени класса |
| 5 | u32 class reference, u32 name-and-type reference |
| 6 | Два u32 reference; различие с 5 требует проверки native/VM-путей |
| 7 | u32 name-string index, u32 descriptor-string index |

После kind 4 **нет обязательного нулевого padding**: следующее нулевое слово часто является kind 0 следующей строки. Публичный C++-парсер использует эвристики, пытаясь компенсировать это. Наш парсер читает типы напрямую: все CONS локального корпуса потреблены точно, без остатков. Короткие строки `I`, `F`, `log` не угадываются по длине.

Строковая кодировка пока интерпретируется как Windows-1252. Для не-ASCII модов кодовую страницу надо проверить отдельно.

## CLSS

Первые пять u32: служебные поля, class reference по +8, superclass reference по +12, данные интерфейсов далее. Для получения имени class reference kind 4 разрешается в строку kind 0. Неизвестные поля сохраняются в raw-секции, не используются как фиктивные флаги доступа.

## MTHD

Два последовательно записанных раздела: u32 число записей первого; записи по 20 байт; u32 число записей второго; записи по 20 байт. Каждая запись — flags, name index, descriptor index, TREE index, local count (пять u32).

Во внешнем разборе есть эвристика с альтернативным порядком полей. Она не потребовалась на исследованном корпусе. Назначение разделов необходимо установить по исходному компилятору/дизассемблированию; не называем их произвольно constructor/native.

В установленном Object `wait` и `runDLL` имеют flags=0x41, `equals`=0x1, статические native-методы вроде Integer.toString — 0x49. Это подтверждает native-бит 0x40 и static-бит 0x8 для этих классов; остальные биты не следует заимствовать из JVMS автоматически. Пустой TREE есть и у обычных `finalize`, `osdCommand`; пустота не доказывает native.

Дескрипторы похожи на JVM, но используют точки в полных именах. Конструктор может иметь `()` без возвращаемого `V`. Сигнатура входит в ключ native-вызова: по одному имени `runMethod` нельзя выбрать перегрузку.

## TREE

u32 tree count; далее для каждого u32 node count и узлы переменной длины: op u8, source/служебное поле u16, optional operand u32. Поле u16 совпадает со строками исходника на проверенных примерах; нельзя считать его индексом регистра.

Узлы имеют 7 байт для op:

```text
01 02 03 06 07 08 09 0A 0B 0D 0E 0F 11 12 14 15 16 17
19 1A 1B 1C 1E 1F 25 26 27 2E
```

Остальные встреченные узлы — 3 байта. Таблица основана на [публичной реконструкции](https://github.com/EliasFD3S/slrr-reverse/blob/5c42f3b139aef4c7b9e0b6420c5704e22c0e6cd7/engine/include/tree_op_flags.inc) и проверена точным потреблением всех TREE-секций. Их семантика **не** совпадает с Java bytecode. Даже имена op в некоторых старых исследовательских инструментах противоречат более поздней реализации того же проекта.

### Первый проверенный запуск

`src/runtime/tree-machine.ts` исполняет небольшой набор leaf-выражений. `npm run verify:vm` загружает **оригинальный** `system/scripts/lang/Object.class` и исполняет его `equals`, не подменяя вызов JavaScript-функцией по имени:

```text
equals(self)  → 1
equals(other) → 0
equals(null)  → 0
```

Для этого подтверждены load local 0x01, block marker 0x03, operator selector 0x07 с operand=7 (равенство), expression evaluate 0x28 и return 0x2b. Дополнительно реализованы непосредственные числа, строки и null; полноценный прогон их семантики ещё необходим. Неизвестный opcode останавливает вызов **до** выполнения тела. Нет молчаливого пропуска команд или подбора аргументов по имени метода.

Это не исполнение всей игровой логики. Нет полей, объектов VM/GC, наследования dispatch, вызовов, массивов, циклов, scheduler Java threads и компиляции `.java`. NativeRegistry пока отдельный контракт; игровые native-функции не реализованы.

## Присланный Object.java

Хеш и размер находятся в `docs/reports/user-source-metadata.json`; сам присланный исходник не скопирован в публичный репозиторий.

Объявляет корневой `java.lang.Object`, wait/notify/notifyAll, toString, hashCode, enableGC/disableGC, runDLL и equals с возвращаемым int. В нём нет runMethod, errorVM, osdCommand, handleOsdEvent. В установленном class эти методы есть, а hashCode отсутствует. Значит, найденный исходник нельзя безусловно считать точной исходной версией установленного Object.class.

Комментарии о пустом finalize и обязательном конструкторе дают ориентир для совместимости, но сами по себе не раскрывают алгоритм GC. Новый движок не должен использовать disableGC как исправление утечки сериализации.

## Почему не просто сторонняя JVM

[Doppio](https://github.com/plasma-umass/doppio) — браузерная JVM; [CheerpJ](https://github.com/leaningtech/cheerpj-meta) — среда исполнения обычных Java-приложений в браузере. Их описания не заявляют поддержку Invictus TUFA/TREE. Потребуется либо преобразование TUFA в стандартный bytecode, либо нормализация исходников и компиляция, плюс собственная системная библиотека native API. Наличие browser-JVM само по себе не решает этот проект.

Текущий выбор — свой декодер и постепенное подтверждение семантики TREE. Возможность WASM-интерпретатора или трансляции в JS остаётся открытой после проверки корректности.
