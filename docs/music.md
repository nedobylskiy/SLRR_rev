# Music integration

The browser music backend reads audio from the selected game installation. `MainMenu.java` is interpreted from source, and its `Sound.changeMusicSet(Sound.MUSIC_SET_MENU)` call reaches the music backend through a native host binding. The original `.class` file is not executed. A different `MainMenu.java` can issue the same supported `Sound` calls without changing the TypeScript menu code.

The five music sets resolve to the original folders: `Main_Menu`, `Garage_Shop`, `Race_Chase`, `Roam_Ride`, and `Misc_Menu`. `MUSIC_SET_NONE` stops playback. The host accepts the Sound calls found in the original Java scripts: `init`, `changeMusicSet`, `firstTrack`, `nextTrack`, `prevTrack`, `randomTrack`, `stopMusic`, `playTrack(int)`, `playTrack(String)`, `getTotalTracks`, `getNowPlaying`, `getVolume`, `setVolume`, `increaseVolume`, and `decreaseVolume`. `playTrack(String)` accepts a path such as `Music\\Main_Menu\\theme.mp3`. Here `getNowPlaying` returns the current file path. Tracks within a set are currently ordered by filename. The exact playlist order and return semantics of the original native `getNowPlaying` have not been recovered.

For new Java scripts, the binding also provides `getTrackTitle()`, `getTrackArtist()`, `getTrackAlbum()`, `getTrackPath()`, `getTrackPosition()`, `getTrackDuration()`, `getTrackIndex()`, `getTrackCount()`, `isTrackPlaying()`, `seekTrack(seconds)`, `pauseTrack()`, and `resumeTrack()`. Position and duration are in seconds; duration is zero until browser metadata is loaded. Title, artist, and album come from common ID3v2 text tags when present. The filename is used as a title when no tag is available.

The local development server streams MP3, OGG, and WAV with HTTP byte ranges, so seeking and duration discovery do not require loading the entire file. A folder selected in the browser is read through the existing asset provider. Browser autoplay policy may require a click on **Play**. The effects and engine volume channels control vehicle audio during a drive.

## Vehicle and spatial audio

During a vehicle drive, the audio layer reads the installed engine block's Java `updatevariables()` source for `getSfxTable()` and `addItem()` calls. Resource IDs are resolved through the matching engine RPK to the original WAV files. Each engine and exhaust layer has the reference RPM, active RPM range, and volume range specified by that block's Java source. The native SfxTable's adjacent-range overlap formula now determines sample weights, while each sample's volume interpolates between its Java minimum and maximum and playback rate follows the reference RPM. A gap or an RPM outside all ranges still uses the nearest sample, as requested for the browser engine; other engine-level gain choices remain approximations. The selected engine determines which samples play, so a different installed block selects its own sound table.

The engine, exhaust, and four tire contacts use 3D panners attached to their positions. The listener follows the camera. Rolling and slipping wheels use the original road, grass, or dirt WAV files; their levels follow wheel speed and contact slip. The original `sound.rpk` identifies `Air.wav` as an air sound; it supplies a speed-dependent wind layer. Effects and engine channel volume changes from Java are applied while driving. Audio starts on a click or vehicle control key when the browser blocks automatic sound. Sources stop when the drive ends.

`gameSoundVolume` in `src/audio/audio-settings.ts` is the shared master level for game sound effects, including the engine, tires, and wind; it does not affect music. The Music panel exposes a separate **Game sounds** slider. The stock Baiern RPK refers to a missing `exhaust_WOT/Baiern/2500RPM.wav`; when a table has an RPM gap after unavailable files are removed, the mixer keeps the nearest available sample from that engine. The mixer raises low-RPM engine audibility and caps its minimum playback rate because the original `2000RPM.wav` is listed with a 3500 RPM pitch reference and otherwise plays too slowly at idle. Wind has been reduced to keep it behind the engine and tires.

Starting a stalled engine plays `sound:0xA` (`engine/ignition.wav`), as declared in `Chassis.java` and `Block.java`. A sharp high-speed lateral slide triggers the separate `surface/skid_ok.wav` onset sound; the existing slip loop continues while the wheels slide. Solid chassis contacts publish their strongest contact impulse and position to the audio layer, which plays the original `sound:0xB/0xC` collision WAV with volume related to the impact speed. The short collision cooldown prevents a four-wheel or multi-iteration contact from repeating the sound every physics tick.

Collision WAVs are fetched and decoded as soon as vehicle audio starts, before the engine table and tire loops finish loading. Ready one-shots start synchronously when physics reports contact. Harder hits mix in `MetalHit2.WAV`, with a quieter `Metal_plane_hit_04.WAV` layer for the strongest impacts.

The collision cue also comes from the first incoming deformable-panel contact with an obstacle. In the 15 km/h fixture this occurs seven 240 Hz physics steps before the rigid chassis contact, so the sound begins with the visible panel hit. Strong-impact layers now have higher gain and pass through a light compressor before the effects channel.

The installed impact WAVs have audible attacks roughly 20–70 ms after their first sample. Collision playback starts at each file's attack (`Collision.wav` 30 ms, `MetalHit2.WAV` 20 ms, and `Metal_plane_hit_04.WAV` 60 ms), and the Web Audio context requests interactive output latency. The exact device output latency is still controlled by the browser and audio hardware.

Tire-squeal volume stays at full level for a stationary burnout and becomes quieter above 29 km/h, reaching 45% around 108 km/h. Skid-mark opacity is full below 36 km/h and fades to 32% of that opacity by 108 km/h. Wheel spin alone does not lighten a stationary burnout mark.
